# Common False Positives in AI-Generated SEO Audits

A catalog of specific claims AI audits routinely make that are usually wrong, plus the rebuttal pattern for each. Refer to this list whenever you're verifying another AI's audit or running your own — match incoming claims against the patterns here before accepting them.

## "No robots.txt found"

**Why it's usually wrong:** The auditor probably didn't actually fetch `/robots.txt`. Most static-site frameworks (Hugo, Jekyll, Next.js, custom build scripts) generate one by default.

**Verify:** `curl -s https://SITE.com/robots.txt | head`

**Rebuttal:** "robots.txt exists at /robots.txt, content: [first lines]. Sitemap reference present: yes/no."

## "Missing XML sitemap"

**Why it's usually wrong:** Same root cause — auditor didn't curl `/sitemap.xml` or check `robots.txt` for the Sitemap directive.

**Verify:** `curl -s https://SITE.com/sitemap.xml | head -5; wc -l < <(curl -s https://SITE.com/sitemap.xml)`

**Rebuttal:** "Sitemap exists at /sitemap.xml with N URLs."

## "Missing canonical tags"

**Why it's usually wrong:** Canonical tags live in `<head>`, and AI auditors often inspect rendered visible content rather than view-source.

**Verify:** `curl -s https://SITE.com/PAGE/ | grep -oE 'rel="canonical"[^>]*'`

**Rebuttal:** "Canonical present on /PAGE/, points to [URL]."

## "No JSON-LD / structured data detected"

**Why it's usually wrong (two separate reasons):**

**Reason 1 — you didn't look in the head.** `<script type="application/ld+json">` blocks live in head or just before `</body>`, invisible to any auditor reading rendered visible content.

**Reason 2 — JSON-LD is not the only syntax, and this one bites hard.** Google reads **three** structured-data syntaxes: JSON-LD, **microdata** (`itemscope` / `itemtype` / `itemprop`), and **RDFa** (`typeof` / `property`). A `grep` for `application/ld+json` returning zero tells you nothing about the other two. Many WordPress themes, page builders, and site builders emit microdata exclusively — so "0 JSON-LD blocks" is routinely a site with perfectly valid, Google-readable markup.

This is the highest-cost false positive in the catalog, because "you have no structured data" is exactly the claim a client's developer disproves in one view-source — and it discredits every other finding in the report.

**Verify all three before any absence claim:**

```bash
curl -s https://SITE.com/PAGE/ | grep -oiF 'application/ld+json' | wc -l          # JSON-LD blocks
curl -s https://SITE.com/PAGE/ | grep -oE '"@type"[^,}]*' | sort -u              # JSON-LD types
curl -s https://SITE.com/PAGE/ | grep -oE 'itemtype="[^"]*"' | sort -u           # microdata types
curl -s https://SITE.com/PAGE/ | grep -oE 'itemprop="[^"]*"' | sort -u           # microdata properties
curl -s https://SITE.com/PAGE/ | grep -oE 'typeof="[^"]*"' | sort -u             # RDFa types
```

**Rebuttal:** "Page declares [types] via [JSON-LD / microdata / RDFa]." If gaps exist, name them at the *property* level rather than the type level.

**The far stronger finding is usually "present but hollow."** A page can declare exactly the right type and populate almost none of the properties that matter. Example from a live audit: a salon declared `schema.org/HairSalon` — a valid `LocalBusiness` subtype — with only `name`, `logo` and `url`. No `address` (which Google lists as *required*), no `telephone`, no `openingHoursSpecification`, no `geo`. "Your markup is incomplete in these four named fields" is precise, checkable, and something a developer will agree with. "You have no structured data" is false. Prefer the first every time.

## "Site has no H1" / heading claims

**Why it needs care:** zero-`<h1>` pages are genuinely common and it is a real finding — but the check must be run, and it must survive the rendering caveat (some builders inject headings client-side).

**Verify:** `curl -s https://SITE.com/ | grep -oiE '<h1[ >]' | wc -l` and pull the full outline with `grep -oiE '<h(1|2|3)[^>]*>[^<]{1,90}'` so you can show the actual hierarchy rather than asserting it.

## "Missing meta descriptions"

**Why it's usually wrong:** Most CMS / build scripts have a default meta description generator; absent ones are usually intentional (e.g., 404 pages, taxonomy pages).

**Verify:** `curl -s https://SITE.com/PAGE/ | grep -oE '<meta name="description"[^>]+content="[^"]*"'`

**Rebuttal:** Cite the actual meta description or confirm absence.

## "Missing Article schema on guide/blog pages"

**Why it's usually wrong:** Article schema is auto-generated by most blogging platforms. The auditor may have looked at non-article pages and generalized.

**Verify:** Check a representative article URL with grep.

## "Wrap decorative icons in role='img' aria-label='...'"

**Why it's WRONG:** This advice is backwards for decorative icons. WCAG 1.1.1 distinguishes decorative from informative imagery. Decorative icons (where adjacent text conveys the meaning) should be HIDDEN from assistive tech, not labeled. Labeling them creates announcement noise.

**The test:** Would a screen-reader user lose meaning if the icon were removed? If no → decorative → `aria-hidden="true"`. If yes → informative → `aria-label` or `alt`.

**Rebuttal:** "Decorative icons should use `aria-hidden='true'`, not `role='img' aria-label='...'`. The adjacent H3 already conveys the meaning; labeling the icon would add noise. (Reference: WCAG 1.1.1 Non-text Content.)"

## "Add FAQ schema for rich snippets"

**Why it's usually STALE:** Google removed FAQ rich results entirely on 7 May 2026 — they no longer appear in search for *any* site, including the authoritative government/health sites that kept them after the August 2023 restriction. (FAQ support also drops from the Rich Results Test in June 2026 and the Search Console API in August 2026.) The structured data is still parsed for entity understanding, but the SERP-treatment benefit is gone for everyone.

**Verify:** Search current Google Search Central docs for "FAQPage structured data" — confirm the May 2026 removal still stands.

**Rebuttal:** "FAQ rich results were removed for all sites in May 2026; FAQPage markup is still parsed for entity understanding but no longer produces any visible SERP rich result. Worth keeping/adding only for entity recognition, not for SERP real estate."

**Do not tell a client to strip existing FAQ markup.** Google has said unused structured data causes no problems for Search. Removing it is make-work.

**Raise this one unprompted when the page has a visible FAQ section.** Automated tools and competing audits still recommend FAQ schema for rich snippets. Saying "the tools will tell you to add this, and it has produced nothing since May 2026" is the cheapest available proof that the audit is current rather than generated.

## "Add HowTo schema" — and the other retired rich-result types

**Why it's STALE:** a batch of rich-result types has been retired, and recommendations for them still circulate widely in tools and training data.

- **HowTo** — removed (2023); documentation and case study withdrawn.
- **Retired in the 2025 search-results simplification:** Book Actions, Course Info, Claim Review, Estimated Salary, Learning Video, Special Announcement, Vehicle Listing.
- **Practice Problems** — deprecation notice added; support removed from Search Console rich-result reporting, the Rich Results Test, and search-appearance filters from January 2026.
- Retired SERP features often confused with structured-data types: nutrition facts, nearby offers and events, local bikeshare station status, TV season selector.

**Verify:** check the type's page in the Search Central structured-data gallery for a deprecation notice before recommending it.

**Rebuttal:** "[Type] no longer produces a rich result. The Schema.org type is still valid and may aid entity understanding, but there is no SERP feature left to earn." Note the distinction that matters: absence from the Rich Results Test means the type is not *eligible*, not that the markup is *invalid*.

## "Add AggregateRating / Review schema to get star ratings" (on a local business)

**Why it's WRONG:** self-serving reviews are ineligible. Google: *"If the entity that's being reviewed controls the reviews about itself, their pages that use `LocalBusiness` or any other type of `Organization` structured data are ineligible for star review feature."* A review about a business, published on that business's own site, is self-serving — including when it arrives through an embedded Google Business or Facebook reviews widget.

So a `LocalBusiness` without `aggregateRating` has **no gap to fix**, and adding it produces nothing.

**Where local stars actually come from:** the Google Business Profile, driven by real GBP reviews. On-site markup is not the lever.

**The trap this creates in competitor analysis.** Finding `AggregateRating` and `Review` in a competitor's markup does *not* mean the competitor is earning stars — plenty of local sites publish ineligible self-serving markup. Before claiming "your competitor is eligible for star ratings and you aren't," run the search and look. A competitive claim the client can disprove in one query is worse than making no claim.

**Rebuttal:** "`aggregateRating` on your own `LocalBusiness` is ineligible for review stars under Google's self-serving review policy, so adding it won't produce them. Star ratings for a local business come from Google Business Profile reviews. Review snippets do still work for `Product`, `Recipe`, `Course` and similar types, where the reviewer isn't the reviewed party."

## "Add AMP"

**Why it's WRONG:** AMP was deprecated as a Top Stories requirement in 2021 and broadly de-emphasized after. Modern sites don't need it.

**Rebuttal:** "AMP is no longer a ranking signal or a Top Stories requirement. Focus on standard Core Web Vitals instead."

## "Add hreflang"

**Why it's USUALLY irrelevant:** Only relevant if the site has multi-language or multi-region versions. Single-language sites should not add hreflang.

**Rebuttal:** "Site is single-language; hreflang would be incorrect to add. If multi-language is on the roadmap, revisit at that point."

## "Use SRCSET on every image" / "Convert all images to WebP"

**Why it's nuanced:** Real wins for hero images and infographics; marginal for icons and small decorative images. Blanket recommendations ignore the build-time cost.

**Verify:** Run PageSpeed Insights — if LCP is image-bound, focus there. If LCP is text or first-contentful-paint, image optimization is a smaller lever.

**Rebuttal:** Recommend only for the specific images identified as LCP bottlenecks or that are large enough to matter (>50KB).

## "Variant pages cause keyword cannibalization, canonicalize them all to parent"

**Why it's a DECISION, not a fix:** Programmatic SEO sites intentionally generate variant pages to catch long-tail queries. The auditor's "consolidate to parent" advice kills that strategy. Both consolidation and self-canonical are defensible — depends on whether variants actually rank.

**Rebuttal:** "Variant pages with unique H1/title targeting distinct queries are a valid pSEO pattern. Consolidating sacrifices long-tail capture for signal concentration. Check Search Console for variant-page impressions before deciding — if they're earning clicks, keep self-canonical; if they're being ignored or chosen-against by Google, consider consolidation."

## "Site is missing X-Content-Type-Options / HSTS / X header"

**Verify:** `curl -sI https://SITE.com/` and check headers directly. Many static-hosting providers (Cloudflare, Netlify, Vercel) auto-add these or they're in the project's `_headers` file.

## Pattern: "the auditor couldn't read the head"

The unifying false-positive pattern is: AI auditors that produce summaries from rendered visible content (post-CSS) cannot see what's in `<head>`. So they confabulate absences for everything that lives in head — meta tags, structured data, link rels, preload hints. Always treat "missing X" claims about head-content as needing curl/grep verification.

When you encounter a new "missing X" claim not on this list, ask: "Is X something that would live in head, _headers, robots.txt, sitemap, or a generated file?" If yes, the claim needs verification before acceptance.

## Pattern: "the advice is from 2-3 years ago"

The other unifying pattern is stale advice. Whenever a recommendation involves:
- Specific structured data types
- Rich-result eligibility
- A "Page Experience" metric or weight
- A Google update name (Helpful Content, Core Update, etc.)
- An algorithm signal (E-E-A-T variants, etc.)

…assume the recommendation may be outdated and web-search the current Google Search Central docs to verify before reporting.
